## Executive Summary

The news article generation workflow has **fundamental architectural issues** that prevent it from functioning as an automated, scalable system. The current implementation relies on **static, hardcoded article metadata** in all 14 language index files, creating a maintenance nightmare and defeating the purpose of automated content generation.

**Key Finding:** The system generates news articles successfully (EN/SV pairs), but the index pages that aggregate and display them use **static JavaScript arrays** that must be manually updated, creating a bottleneck that undermines automation.

## 2. Identified Problems

### 2.1 🔴 CRITICAL: Static Article Arrays in Index Files

**Problem:**
All 14 `news/index_*.html` files contain hardcoded JavaScript arrays that must be manually updated when new articles are created.

**Impact:**
- Automation workflow generates articles successfully
- BUT: Index pages don't reflect new articles until manually updated
- Creates a critical bottleneck in the automation pipeline

**Evidence:**
- `news/index.html` lines 304-377: hardcoded 8-article array
- All 14 language indexes have identical arrays
- No dynamic article discovery mechanism

**Why This Exists:**
The current design uses a **client-side only** approach with no build step:
- Static HTML files served directly (GitHub Pages)
- JavaScript renders articles from hardcoded arrays
- No server-side generation (no Node.js at runtime)
- No build tool integration (Vite is only for dashboard, not news)

---

### 2.2 🔴 CRITICAL: Missing Dynamic Article Aggregation

**Problem:**
No system exists to automatically discover and aggregate article metadata from the file system or a database.

**What's Needed:**
1. **Build-time aggregation** - Scan news/ directory, extract metadata, generate index files
2. **Client-side aggregation** - Load articles.json via fetch(), render dynamically
3. **Hybrid approach** - Pre-generate article list during build, enhance with client-side features

**Current Gap:**
- ✅ Articles have YAML frontmatter (in HTML comments)
- ❌ No system to parse frontmatter and extract metadata
- ❌ No articles.json or equivalent data file
- ❌ No build script to regenerate index files

**Hypothesis:** The original implementation prioritized:
1. **Simplicity:** No build step, no Node.js at runtime
2. **GitHub Pages compatibility:** Pure static hosting
3. **Fast development:** Hardcode 8 articles, ship MVP
4. **Client-side rendering:** Modern SPA-like experience

**Trade-offs Accepted:**
- ❌ Manual maintenance burden
- ❌ Doesn't scale beyond 10-20 articles
- ❌ Defeats automation purpose

**Hypothesis:** Forward-thinking design for eventual 14-language support.

**Current State:**
- Index pages created for all 14 languages

- RTL support (AR/HE) exists but unused

**Decision Point:** Keep 14 indexes (future-proof) or reduce to EN/SV (realistic)?

## 4. Recommended Solutions

### 4.1 🎯 PRIMARY SOLUTION: Implement Dynamic Article Aggregation

**Goal:** Eliminate hardcoded article arrays, enable true automation.

**Approach 1: Build-Time Generation (Recommended)**

Generate `news/index*.html` files dynamically during the build/deployment process.

**Implementation:**

1. **Create `scripts/generate-news-indexes.js`:**
   ```javascript
   // Scan news/ directory for article files
   // Parse YAML frontmatter from HTML comments
   // Extract metadata (title, date, excerpt, topics, tags)
   // Group by language (EN articles → index.html, SV → index_sv.html)
   // Render index.html using template
   // Support 14 languages with fallback to EN
   ```

2. **Update workflow `.github/workflows/news-generation.yml`:**
   ```yaml
   - name: Generate news articles
     run: node scripts/generate-news.js
   
   - name: Regenerate news indexes  # ⬅️ ADD THIS
     run: node scripts/generate-news-indexes.js
   
   - name: Update sitemap
     run: node scripts/generate-sitemap.js
   ```

3. **Benefits:**
   - ✅ Fully automated end-to-end
   - ✅ Scales to 1000+ articles
   - ✅ No manual maintenance
   - ✅ Supports all 14 languages
   - ✅ GitHub Pages compatible (static output)

**Approach 2: Client-Side JSON Loading**

Keep index HTML files static, but load article metadata from JSON.

**Implementation:**

1. **Create `news/articles.json`:**
   ```json
   {
     "lastUpdate": "2026-02-12T10:00:00Z",
     "articles": [
       {
         "slug": "2026-02-10-week-ahead-feb-10-17",
         "languages": ["en", "sv"],
         "en": {
           "title": "Week Ahead: Brussels Summit Tests Swedish EU Strategy",
           "date": "2026-02-10",
           "excerpt": "Critical week for Swedish European policy...",
           "topics": ["eu", "defense"],
           "tags": ["EU Summit", "Brussels"]

           "excerpt": "Kritisk vecka för svensk Europapolitik...",
           "topics": ["eu", "defense"],
           "tags": ["EU-toppmöte", "Bryssel"]
         }
       }
     ]
   }
   ```

2. **Modify `news/index.html`:**
   ```javascript
   // Remove hardcoded articles array
   let articles = [];
   
   // Fetch articles from JSON
   fetch('./articles.json')
     .then(res => res.json())
     .then(data => {
       articles = data.articles.map(a => ({
         ...a.en,  // Use 'en' for English index

       renderArticles(articles);
   ```

3. **Benefits:**
   - ✅ Simpler implementation
   - ✅ Dynamic updates without regenerating HTML
   - ✅ Better for API-driven content

4. **Drawbacks:**
   - ⚠️ Requires JavaScript (no SEO without SSR)
   - ⚠️ Extra HTTP request on page load

**Recommendation:** Use **Approach 1 (Build-Time Generation)** because:
- Better SEO (static HTML with article metadata)
- No runtime dependencies
- Consistent with current architecture (no build step for dashboard)
- Backward compatible

### 4.3 🎯 TERTIARY: Multi-Language Translation Strategy

**Goal:** Support all 14 languages, not just EN/SV.

**Option A: Generate EN First, Then Translate (Recommended)**

**Workflow:**
1. Generate English article (primary content)
2. Generate Swedish article (high-priority translation)
3. Auto-translate to 12 other languages (lower priority)

**Implementation:**
```javascript
// After generating EN article
async function translateArticle(slug, fromLang = 'en', toLang) {
  const sourceFile = `${slug}-${fromLang}.html`;
  const source = await parseArticleHTML(sourceFile);
  
  // Translate metadata and content
  const translated = await translateContent(source, toLang);
  
  // Render translated article
  const targetFile = `${slug}-${toLang}.html`;
  await writeArticleHTML(targetFile, translated, toLang);
  
  return targetFile;
}

// Generate all 14 language versions
async function generateAllLanguages(slug, enData) {
  const languages = ['sv', 'da', 'nb', 'fi', 'de', 'fr', 'es', 'nl', 'ar', 'he', 'ja', 'ko', 'zh'];
  
  for (const lang of languages) {
    if (lang === 'sv') {
      // Swedish: Manual high-quality generation
      await generateSwedishArticle(slug, enData);
    } else {
      // Others: Auto-translate from English
      await translateArticle(slug, 'en', lang);
    }
  }
}
```

**Translation Service Options:**

3. **Azure Translator** - Good quality, free tier (2M chars/month)
4. **LibreTranslate** - Open source, self-hosted, lower quality

## 6. Risk Assessment

### 6.1 Technical Risks

**Risk 1: MCP Server Availability** 🔴 HIGH
- **Threat:** riksdag-regering-mcp server down or rate-limited
- **Impact:** Articles can't be generated
- **Mitigation:**
  - Implement retry logic with exponential backoff
  - Cache previous responses for 24 hours
  - Fallback to manual article creation if MCP fails

**Risk 2: Translation Quality** 🟠 MEDIUM
- **Threat:** Auto-translated articles contain errors or cultural issues
- **Impact:** Reputation damage, misinformation
- **Mitigation:**
  - Keep EN/SV as manually generated (highest quality)
  - Add "Automatically translated" disclaimer to other languages
  - Implement editorial review workflow for critical articles

**Risk 3: Build-Time Generation Complexity** 🟡 LOW
- **Threat:** `generate-news-indexes.js` fails to parse articles
- **Impact:** Indexes not updated, articles hidden
- **Mitigation:**
  - Extensive error handling and logging
  - Fallback to previous index if generation fails
  - Alert on script failures

---

### 6.2 Process Risks

**Risk 4: Workflow Timing Conflicts** 🟠 MEDIUM
- **Threat:** News generation and data pipeline run simultaneously
- **Impact:** Race conditions, file conflicts
- **Mitigation:**
  - Use workflow concurrency limits
  - Implement file locking
  - Schedule workflows at different times

**Risk 5: Manual Index Updates During Transition** 🟡 LOW
- **Threat:** Someone manually updates index while automation is being implemented
- **Impact:** Changes overwritten by automated script
- **Mitigation:**
  - Add warning comments to index files
  - Lock index files during development
  - Communicate with team about transition

---

### 6.3 Data Risks

**Risk 6: YAML Frontmatter Parsing Errors** 🟠 MEDIUM
- **Threat:** Malformed frontmatter breaks index generation
- **Impact:** Article excluded from index
- **Mitigation:**
  - Robust YAML parser with error recovery
  - Validate frontmatter schema
  - Log parsing errors for debugging
